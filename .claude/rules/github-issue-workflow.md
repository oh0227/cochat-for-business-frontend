# GitHub Issue Workflow

## 규칙: 코드 수정 전 반드시 이슈를 먼저 등록한다

버그를 발견하거나 기능을 추가하기 전에, **항상 GitHub 이슈를 먼저 생성한 뒤 코드를 수정**한다.

### 이슈 등록 대상 레포

- **대상 레포**: `oh0227/cochat-for-business-frontend` (groomthon-12/cochat-frontend의 포크 — upstream이 아닌 이 포크에 등록한다)

### 이슈 등록 절차

1. 문제 또는 작업 내용을 파악한다
2. 기존 이슈와 연관성을 확인한다
   - 연관 있으면 → **sub-issue**로 등록 (본문에 `parent: #번호` 명시)
   - 연관 없으면 → 새 독립 이슈로 등록
3. 이슈를 생성한다 (`gh issue create --repo oh0227/cochat-for-business-frontend ...`)
4. 이슈 번호를 확인한 뒤 코드 수정을 시작한다
5. 커밋 메시지에 `closes #번호` 또는 `refs #번호`를 포함한다

### Sub-issue 작성 규칙

GitHub에 공식 sub-issue 기능이 없으므로 본문 상단에 아래 형식으로 표기한다:

```
## 관련 이슈

parent: #2 (상위 이슈 제목)
```

### 이슈 본문 포함 항목

- **문제 요약**: 한 줄 설명
- **에러 로그**: 실제 로그 또는 스택트레이스
- **원인 분석**: 어느 파일 몇 번째 줄, 왜 발생하는지
- **영향 범위**: 관련 파일 목록
- **해결 방안**: 적용할 접근법 (선택지가 여러 개면 후보로 나열)

### 브랜치

모든 수정은 `dev` 브랜치 기준으로 작업한다.

---

## 규칙: 이슈 종료는 사용자가 직접 확인한 후에 한다

코드를 수정하고 push했다고 해서 이슈를 바로 닫지 않는다.

이 프론트엔드는 별도로 배포하지 않고 **로컬 dev 서버(localhost)에서 실제 프로덕션 백엔드에 연결해 확인**하는 방식으로 운영한다. "배포 서버 확인"이 아니라 "로컬 브라우저 확인"이 종료 기준이다.

### 이슈 종료 절차

1. 코드 수정 완료 후 push
2. **사용자에게 로컬 dev 서버(브라우저)에서 확인을 요청**한다
   - "로컬에서 확인해 주시면 이슈를 닫겠습니다."
3. 사용자가 "해결됐다", "잘 됨", "확인했다" 등 확인 응답을 주면 그때 이슈를 닫는다
   ```bash
   gh issue close <번호> --repo oh0227/cochat-for-business-frontend --comment "로컬 dev 서버에서 정상 동작 확인 완료."
   ```
4. 사용자가 "아직 안 된다"고 하면 원인을 재분석하고 새 수정을 진행한다

### 금지 사항

- 커밋 메시지의 `closes #번호`만으로 이슈를 닫는 것에 의존하지 않는다
  (GitHub 자동 close는 PR merge 기준이므로 push만으로는 닫히지 않음)
- 코드가 로컬에서 올바르다고 판단(=AI 혼자 판단)해서 사용자 확인 없이 임의로 이슈를 닫지 않는다
